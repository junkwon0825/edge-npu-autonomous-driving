# 이력서용 프로젝트 요약 (한국어)

**프로젝트:** Edge-NPU Autonomous Driving Perception & Control System. 개인 연구 프로토타입이며 CARLA
0.9.16 시뮬레이션에서만 검증했습니다. 모든 수치는 `reports/evidence/`에 기록된 실행 결과입니다.

## 한 줄 버전
Furiosa RNGD NPU에 객체 검출·차선 분할 모델을 배포하고, 장애 시 GPU로 전환하는 멀티모델 런타임을
만들었습니다. 이를 CARLA 폐루프 긴급제동(AEB)·차선유지(LKA)에 통합해, 모델 지연이 아니라 시스템 지연이
차량 거동을 어떻게 바꾸는지 정량화했습니다.

## 이력서 3줄 버전
- **NPU 포팅:** YOLO26n(BF16 2.0 ms)과 컴파일러 제약에 맞춰 설계한 차선 U-Net(2.8 ms)을 Furiosa
  RNGD에 이식했습니다.
  - 74건의 연산자 호환성 DB와 6가지 정확한(exact) 그래프 변환으로 미지원 연산을 해결했고, YOLO26s도
    컴파일되게 했습니다.
  - INT8 연산이 SDK에서 불가함을 컴파일러 probe로 입증했습니다.
- **런타임·전송:** 프레임 나이(frame age)를 관리하는 비동기 런타임을 구축했습니다. 최신 프레임 큐,
  오래된 결과 차단 게이트, 2-PE 멀티모델 서버, 로그가 남는 GPU 장애 전환으로 구성됩니다.
  - 단계별 프로파일링으로 원격 NPU 왕복 시간을 203 → 60 ms로 무손실 단축했습니다.
  - 4 PE에서 초당 1,762회 추론까지 확장했습니다.
- **폐루프 평가:** 카메라 기반 AEB + LKA(레이더 융합 포함)를 CARLA 폐루프 80회로 평가했습니다. 위험
  시나리오 36회 충돌 0회, 직선·완만한 커브·야간·우천 경로에서 차선 RMSE 0.8–2.6 cm였습니다.
  - 위험 사례도 보고했습니다. 원격 데이터 지연으로 50 km/h 제동 여유가 13.7 m에서 2.1 m로
    줄었습니다.
  - 야간·우천 차선 실패의 원인이 NPU 정밀도가 아니라 요청 타임아웃임을 규명했습니다.

## 상세 포트폴리오 버전
**문제의식:** NPU 모델이 빠르다고 주행 루프가 안전해지지는 않습니다. 이 프로젝트는 카메라에서
액추에이터까지 시간이 어디에 쓰이는지, 그리고 그 시간이 제동과 조향에 어떤 영향을 주는지 측정합니다.

**V1: GPU 폐루프 + NPU 검증**
- **폐루프:** CARLA 카메라 → YOLO26n → 단안 거리·TTC → AEB. 30 km/h 위험 시나리오 30회에서 충돌
  0회였습니다.
- **NPU 배포:** 컴파일 실패 원인(BatchNorm 미융합, head concat)을 진단했습니다. 모델을 raw head에서
  분할하고 decode/NMS는 host에서 처리했으며, 원본과 72/72 프레임 일치를 확인했습니다.
- **공정한 GPU 기준선:** CUDA Graph 2.60 ms vs eager 13.54 ms. 겉보기 "NPU 6배"는 실제로 1.2–1.4배였습니다.
- **INT8:** W8은 가중치 전용입니다. 가중치는 4.82 → 2.44 MB로 줄지만 더 느리고(2.35 vs 2.00 ms),
  진짜 INT8 연산은 툴체인에서 막혀 있습니다.

**V2: 비동기 런타임 + 강건한 AEB**
- **전송:** 원격 경로 단계별 프로파일링(203 → 60 ms). 페이로드 축소, 스레드 고정, 정확한 사전 필터,
  SSH 압축을 적용했습니다.
- **런타임:**
  - 백엔드 추상화(GPU / RNGD / replay)
  - 최신 프레임 큐
  - 프레임 나이 게이트
  - 명시적 장애 전환
- **인지·제동:**
  - SORT 방식 추적기와 거리 칼만 필터
  - 경로 예측 AEB. 위험 시나리오 충돌 0/18(V1: 2/18), 인위적 지연 200 ms까지 무충돌
- **라이브 루프:** 원격 RNGD를 실시간 CARLA 루프에 연결해 동작시켰지만, 준실시간 수준입니다(프레임 나이
  p95 165–212 ms).

**V3: 멀티모델 NPU 인지 + LKA + 센서 융합**
- **차선 모델:** 실측한 컴파일러 제약에 맞춰 차선 U-Net을 설계했습니다. 256×512에서 풀링이 실패하므로
  3×3 stride-2 다운샘플링과 정확한 업샘플링 변환을 사용합니다.
- **멀티모델 서버:** 검출은 PE 0, 차선은 PE 1에서 실행하며 업로드는 한 번입니다(원격 61 ms, 검출 단독
  55 ms). 요청 병합 디스패처로 차선 요청이 굶는 버그를 수정했습니다.
- **제어:**
  - 카메라 전용 pure-pursuit LKA(차선 데이터 나이 보상, 0.5 s 타임아웃)
  - 제동 중 조향을 ±0.1로 제한하는 중재기
  - 레이더 융합 1단계
- **평가:** 폐루프 80회. 차선 유지(A–D 모드 × 경로), 커브 AEB + LKA 복합, 레이더 비교, 스케줄링
  전략, 장애 주입, 차선 데이터 나이 스윕을 포함합니다.
- **결과:**
  - 위험 시나리오 36회 충돌 0회
  - 정상 세션 차선 이탈 0회
  - 차선 데이터 나이 허용 한계 약 0.25 s
  - 제동 29,618 tick 모두 |steer| ≤ 0.10
- **실패 분석:** 야간·우천 차선 실패는 처음에 BF16 문제처럼 보였습니다.
  - 동일 프레임 440장으로 GPU vs NPU를 비교한 결과 RNGD = GPU BF16(IoU 0.991–0.998)이었습니다.
  - 실제 원인은 호스트 메모리 부족 상황에서 발생한 원격 요청 타임아웃, 그리고 차선 fallback의
    부재였습니다.
  - 정상 세션 재실행에서는 이탈 0회였습니다.

**정직한 한계:**
- 50 km/h 원격 데이터 지연(제동 여유 2.1 m)
- 오래된 검출 20 %(간격 0.33 m)
- 두 가지 시나리오 유형에서 레이더 융합 악화
- 급커브 불필요 제동
- 셀당 1회 실행
- 시뮬레이션 한정

## 기술 면접 버전
- **모델 지연 vs 시스템 지연:**
  - RNGD에서 YOLO26n 실행은 2.0 ms입니다.
  - 루프 안에서는 원격 요청 63–65 ms(평균), 검출 데이터 나이 121–126 ms(p95)이고, 로컬 GPU는 30 ms입니다.
  - 제어 품질을 좌우하는 것은 데이터 나이입니다.
- **포팅 방법:**
  1. 컴파일러 오류 메시지를 읽습니다.
  2. CPU에서 원본 연산과 비교 검증한 정확한 변환을 작성합니다.
  3. 다시 컴파일합니다.
  4. 형상에 따라 달라지는 제약(풀링)은 학습 전에 아키텍처를 바꿉니다.

  변환은 모두 6가지입니다. YOLO26s는 64 KiB 가중치 슬라이스 제한 때문에 출력 채널 SplitConv가
  필요했고, ResNet18은 입력 채널 분할이 필요해 아직 미해결입니다.
- **스케줄링:**
  - 오프라인에서는 모델별 PE 분리가 최선이고, 한 PE에 워커 두 개는 순차 실행보다 나쁩니다.
  - 루프 안에서는 전송이 지배적이라 모든 전략의 주행 결과가 같습니다. 그래도 적응형 우선순위는
    프레임 드롭을 170 → 21로 줄였습니다.
- **장애 전환:** PRIMARY / FALLBACK / DEGRADED 상태이며 모든 전환을 로그로 남깁니다. 정지 → GPU 0.54 s,
  크래시 → GPU 0.11 s. fallback 지연에는 실패한 NPU 대기 시간이 포함됩니다(이전에는 버그로 누락됨).
- **디버깅 원칙:** 결과가 지나치게 좋아 보일 때 의심해서 시뮬레이터·런타임 버그 3건을 찾았습니다.
  - Mode D 차선 요청 aliasing
  - 숨겨진 장애 전환 대기 시간
  - 효과 없던 stale 주입

  모두 단위 테스트와 함께 수정했고, 영향받은 실행은 별도로 재실행했습니다.
- **다음 단계:**
  - NPU를 카메라 옆에 배치(zero-copy, C++ 클라이언트)
  - 기본 차선 fallback
  - 전처리 통일
  - AEB 대상 상태 로깅
  - 신뢰구간을 위한 반복 실행
