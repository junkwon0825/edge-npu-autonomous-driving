# V1 Final Report — CARLA-NPU Autonomous Driving Perception System

Release candidate `v1.0.0-rc1`, branch `feature/portfolio-hardening`, 2026-11-24. Local only; nothing
pushed. Evidence index: `reports/v1/evidence_manifest.json` (SHA-256 of 46 evidence/plot/config/demo
files). The v3 matrix, quarantined runs, re-runs, benchmark evidence and earlier plots are referenced
in place and were not modified.

## V1 Scope
- **In scope:**
  - closed-loop CARLA AEB with camera YOLO on the local GPU (perception-driven mode emphasised)
  - GPU benchmark with an optimised baseline (CUDA Graphs)
  - real Furiosa RNGD deployment (BF16 primary), validated offline
  - GPU vs NPU comparison
  - documented failures and limitations
- **Out of scope (explicitly not a V1 requirement):** a live NPU inside the CARLA closed loop.

## Architecture
`assets/diagrams/v1_architecture.png` (generated by `scripts/make_v1_diagram.py`):
1. **Runtime closed loop, implemented.** CARLA RGB → YOLO26n (GPU, eager FP32) → flat-ground range +
   CIPO tracker → AEB v2 with measured latency as actuation delay → CARLA vehicle control.
2. **NPU validation path, implemented and offline.** Captured/replay frames → `furiosa-torch` AOT
   compile → RNGD BF16 → the same host decode/NMS → agreement, latency, power and AEB replay.
3. **V2 target, not implemented.** Real-time NPU in loop 1.

Module detail: `docs/architecture.md`.

## CARLA Demo
**Command.** With CARLA started separately (`C:\CARLA_0.9.16\CarlaUE4.exe -RenderOffScreen
-carla-rpc-port=2000`), run `.\.venv\Scripts\python.exe scripts\run_v1_demo.py`.

**Steps:**
1. Check the CARLA connection.
2. Load the GPU detector and warm it up.
3. Spawn the ego vehicle, the pedestrian, the camera and the collision sensor.
4. Run the settle phase.
5. Run the perception → AEB → control loop.
6. Clean up the actors.
7. Write `outputs/v1/demo/{demo.mp4, detection.png, aeb_active.png, final.png, logs/, summary.json}`.

**Scenario:** `pedestrian_crossing`, `mono` (camera only), `gpu_p95` = 22.7 ms delay, 30 km/h.

| Metric (two consecutive runs, identical outcome) | Value |
|---|---|
| Collision | no |
| Minimum gap | 2.68 m (v3 matrix cell, same configuration: 2.68 m) |
| Brake commanded / applied | t = 2.67 s / 2.70 s (3 ticks of delay) |
| GT gap / GT TTC at first applied brake | 6.91 m / 0.83 s |
| Braking distance | 4.31 m |
| Monocular range error | MAE 0.10 m, p95 0.26 m (n = 79) |
| In-loop perception e2e (CARLA sharing the GPU, n = 342) | mean 22.4 ms, p95 27.8 ms, p99 32.2 ms |
| Wall clock | 21.8 s for 3.4 s simulated (≈ 25 Hz loop; not real-time) |

- 0 vehicles, walkers and sensors left in the world
- synchronous mode restored to off

## GPU Results
**Runtime:** PyTorch 2.14.1+cu126, CUDA 12.6, cuDNN 9.10.2, driver 616.92, RTX 3060 12 GB.

**Model:** YOLO26n (`ultralytics` 8.4.202), 640×640 letterbox, FP32. Host decode plus NMS (conf 0.25,
IoU 0.7, max_det 300).

**Batch 1, CARLA stopped:**
- eager: mean 13.54 / p95 18.43 / p99 25.19 ms, n = 360, 72 fps
- **CUDA Graph: mean 2.60 / p95 3.01 / p99 3.23 ms, n = 300, 387 fps**, outputs bit-identical to eager

**Batch sweep (eager):** batch 8 gives 2.45 ms per frame (408 fps).

**Cold first inference:** 388 ms.

**Contention:** with CARLA running on the same GPU, the detector is 58 % slower.

## NPU Results
**Stack:** Furiosa RNGD (`npu0`, firmware 2026.4.0), `furiosa-torch` 2026.4.0 (rev 5800e2ba24),
torch 2.10.0+cpu, Python 3.11.18.

**Compiler config:** `implicit_type_casting`, `lowering_mode Optimal`, `num_pe 8`.

**Input:** static 1×3×640×640 float, the identical letterboxed frames used on the GPU.

**Output:** raw box/score tensors, decoded with the GPU's host code.

**Timing protocols:**
- `bench`: H2D for each frame, then stream synchronise; n = 216
- `perf`: inputs resident on the device, n = 500, plus a 20 s sustained run with `furiosa-smi` power
  sampling

| Variant | bench mean / p95 / p99 (ms) | perf mean (ms) | fps | Power | Agreement vs GPU (recall / precision) |
|---|---|---|---|---|---|
| FP32 | 2.107 / 2.119 / 2.125 | 2.149 | 470 | 53.3 W | 0.988 / 0.992 |
| **BF16 (V1)** | **2.000 / 2.020 / 2.071** | **1.854** | **543** | 53.6 W | 0.972 / 0.992 |
| W8 weight-only | 2.352 / 2.371 / 2.682 | 2.155 | 446 | 51.2 W | 0.957 / 0.980 |

**Other RNGD measurements:**
- idle power 39 W
- first inference 2.47 ms (FP32)
- compile 1162–1902 s
- replay of 616 frames: recall 0.987, precision 0.989, IoU 0.994
- AEB first-brake decision identical to the GPU in 7 of 7 replays

> **Power is indicative only.** GPU power comes from NVML at 50 ms sampling, NPU power from
> `furiosa-smi` at 1 W resolution and ~0.7 s sampling. Both are board level. The derived energy per
> frame (≈ 113 mJ for RNGD FP32 vs ≈ 351 mJ for GPU CUDA Graph) is not a controlled efficiency
> measurement.

**Transport, desktop → remote RNGD:** 121.2 ms mean / 124.8 ms p95 per 1.23 MB frame (n = 30). A
60 kB payload takes 8.5 ms and a ping 3.6 ms.

## Failed Experiments
| Experiment | Outcome | Disposition |
|---|---|---|
| Pipelined NPU execution (8 in flight before one sync) | HAL sync timeout, then `PXI-122 Duplicate submission` | Burst default set to 1; health check PASS; not retried |
| W8 as a speed optimisation | Not faster than BF16, lower agreement | Reported as a negative result |
| True INT8 (W8A8) | Blocked (see SDK limitations) | Probe evidence kept |
| Live pytest during the v3 matrix | 6 runs contaminated, 1 really changed (4.78 → 9.04 m) | Quarantined (kept), re-run; server lock and opt-in live tests added |
| First monocular range calibration | +35 % range error (camera height measured while the car was still falling) | 1 s settle phase |

## SDK Limitations
Found with `furiosa-torch` 2026.4.0 (`remote/int8_probe.py`, `reports/evidence/npu_int8_probe*.json`):
- int8 convolution compiles, but accumulates in int8 with wrap-around: 100 % of outputs wrapped, 0.4 %
  exact.
- int32-accumulating convolution fails with `O117 not yet supported`.
- `aten::_int_mm` cannot be imported.
- FP8 (e4m3) convolution compiles. It was not evaluated for accuracy.

Device-level constraints:
- Device memory is not observable per variant (`furiosa-smi status` reports 0.00 GiB).
- The compiler cache is shared on the host, so compiled artefact size cannot be attributed to one
  variant.

## Known Limitations
1. **The NPU is not in the real-time CARLA closed loop.** NPU latency enters only as an injected
   actuation delay; NPU inference is validated offline.
2. **Remote SSH frame transport is about 120 ms per frame,** which caps a remote loop at ≤ 8 Hz.
3. **True INT8 compute is blocked** by the current Furiosa SDK and toolchain path.
4. **Monocular range-rate estimation is noisy** (MAE 1.2–3.2 m/s, p95 14 m/s beyond 30 m), and it
   causes premature stops.
5. **High-speed pedestrian scenarios remain unsafe** (40 km/h collision; 50 km/h AEB-induced side
   collision).
6. **The controller lacks target-clear and trajectory-prediction logic,** and its latch is permanent.
7. **CARLA rendering causes small run-to-run variation.** GPU inference is deterministic (738 frames
   run twice, diff 0.0).

Further limits:
- **Scope:**
  - one map, one seed per cell, a single target per scenario
  - flat-ground assumption
  - agreement with the GPU instead of mAP (no GT labels)
  - NPU batch > 1 not compiled
  - shared RNGD host
- **Delay model:** the injected GPU delay (22.7 ms p95, CARLA stopped) is about 5 ms below the
  in-loop p95 measured while CARLA shares the GPU (27.8 ms).

## V2 Roadmap
- **V2.1 Range-rate filtering:** a Kalman or α-β filter on monocular range. Acceptance: closing-speed
  MAE below 1 m/s beyond 30 m, and no premature stop in `static_obstacle`.
- **V2.2 Target-clear / trajectory prediction:** predict lateral motion and release the latch when the
  target will clear. Fixes the 50 km/h side collision.
- **V2.3 High-speed pedestrian scenarios:** earlier hazard anticipation (path prediction, wider
  look-ahead) for 40–50 km/h.
- **V2.4 True NPU-in-the-loop:** RNGD replaces the GPU detector in loop 1, with real frame-rate limits.
- **V2.5 Low-latency NPU transport/runtime:** co-located NPU or compressed/ROI transport. Target: a
  perception e2e p95 below 30 ms.
- **V2.6 Optional ROS 2 / Autoware integration.**

Each V2 run writes new result files; the v3 evidence stays frozen.
